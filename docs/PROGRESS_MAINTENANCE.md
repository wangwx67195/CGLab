# Agent 进度维护与证据规范

> 一句话：**进度不是聊天印象，而是能被文件、测试或学生明确确认支持的记录。**

## 1. 文件职责与优先级

| 文件 | 职责 | 更新频率 |
|---|---|---|
| `docs/LEARNING_PLAN.md` | 28 课总体路线、学习目标、依赖 | 仅在用户同意调整计划后 |
| `docs/LEARNING_PROGRESS.md` | **唯一权威的当前课、状态、下一步** | 每次实际学习会话结束时，存在进度变化则更新 |
| `docs/lessons/LXX_*.md` | 该课的题目、验收与提示；无需每天重写 | 课程发布或用户批准修订时 |
| `docs/notes/LXX_notes.md` | 学生自己的推导、困惑、实验记录 | 用户自愿；Agent 可整理但不能编造 |
| `results/` | 经挑选的、能复现的截图/小图 | 用户许可后记录；大量中间图放 `outputs/` 且默认忽略 |

## 2. 状态机

- `not_started`：尚无有效学习或代码证据；
- `in_progress`：已开始阅读、推导、编写或调试，尚未全部完成核心验收；
- `blocked`：有明确障碍阻止继续，必须列出具体阻塞及解除条件；
- `review`：核心实现已有证据，但缺理解检查、边界测试或用户复核；
- `completed`：**同时**满足核心作品可运行、核心用例验证、学习者能解释关键原理（或明确口述/书面确认）、进度归档。

建议状态只允许 `not_started → in_progress ↔ blocked → review → completed`；从 `completed` 撤销必须说明新证据。

## 3. 一次会话的更新流程

**会话开始**：先读进度文件，不默认上次已完成。若已 `in_progress`，续接上次记录的 `next_action`，不要开启新课。

**会话进行中**：若只是询问 API，可保持状态不变；若开始实现，将状态标记为 `in_progress`。如果有工具权限，未经学生同意**不得自动覆盖学生代码**。

**会话结束**：

1. 收集证据：学生声明、实际编译/测试输出、本人检查的源码路径、图像路径、Git SHA（如有）。
2. 明确区分 `observed`（Agent 真的运行/检查）、`user_reported`（学生说已完成）、`planned`（只安排了任务）；不可把后两者写为真实测试通过。
3. 更新 `docs/LEARNING_PROGRESS.md`：更新状态、实做事项、卡点、验证、下一步、最近更新日期。
4. 不删除历史记录，只追加 1 行历史摘要或引用对应笔记；保持“当前状态”区块简短。
5. 只有满足完成标准才把本课标为 `completed` 并指向下一课；如缺理解检查设为 `review`。
6. 如切换到下一课且对应课程卡片尚不存在，先按照 `docs/templates/LESSON_TEMPLATE.md` 和课程总纲创建**任务卡**（不创建答案代码）；当前课保留为 `completed` 历史记录，新课初始为 `not_started`。
7. 在回复里概述本次更新，若没有文件编辑权限则给出精确的待更新文字，不谎称已写文件。

## 4. 进度文件字段规则

`docs/LEARNING_PROGRESS.md` 至少包含以下字段：

- `Current Lesson`：课程 ID 和名称（例如 `L01 · CPU Framebuffer`）；
- `Status`：上面的状态之一；
- `Last Updated`：**实际日期**，不能用未来日期；
- `Goal`：本课目标；
- `Completed`：有证据支持的事项；
- `Evidence`：每一条记录来源标记（`observed`、`user_reported`、`planned`），加路径/命令/结果；
- `Open Questions`：尚未理解的概念；
- `Next Action`：**一个最小可执行任务**；
- `Lesson History`：每课最多一行里程碑，加时间与记录索引。

对路径使用相对项目根目录的路径。引用 Git 提交时用 `git rev-parse --short HEAD` 实际结果，不能虚构 hash。

## 5. 示例：什么时候可以标记完成？

| 事件 | 状态或记录 |
|---|---|
| 只阅读了 L01 文档 | `in_progress`，记录阅读，不算作品完成 |
| 学生说“已经写好了”但未见源码或运行 | `review` 或 `in_progress`；标记 `user_reported`，列需验证事项 |
| 编译过了，但输出文件损坏 | `in_progress`，记录构建成功与图片失败 |
| 生成 PPM，四角颜色正确，但不能解释 `(y*w+x)*3` | `review`，补理解检查 |
| 核心图像、角点检查、边界测试和原理解释齐备 | `completed`；安排 L02 |

## 6. 防止 Agent 自说自话

- **不**随意升级进度、修改课程编号或跳课；
- **不**把示范代码生成视为学生练习完成；
- **不**因某个测试通过就隐藏其他失败；
- **不**私自 `git reset --hard`、`git clean -fd`、`git push --force`、覆盖原本学生手写代码；
- **不**将机器特有路径、密码、令牌或大文件写入 Git；
- **不**把原课程官方作业判为“官方通过”。

## 7. 多设备同步约定

- 开始修改前优先查看 `git status` 与当前分支，不在未提交更改上强行 `pull`；
- 若需同步，先核对远端与本地状态，建议常规 `git fetch` / `git pull --rebase`（**仅在工作树干净且操作获授权时**）；
- 合并冲突时保留学生手写代码和进度证据，不自动丢弃任一端；
- 每次完成课后建议以 `lesson(L01): ...`、`docs(progress): ...` 等清晰的提交信息保存，但是否 commit/push 由用户决定。
